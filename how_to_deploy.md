# Руководство по развертыванию, запуску и защите проекта
## Веб-приложение «Система учета домашних заготовок» (ПР1 – ПР7)

Данный документ содержит пошаговую инструкцию по локальному запуску системы, подробный разбор архитектуры и сущностей, а также готовые ответы на типовые вопросы преподавателя для успешной защиты работы.

## 1. Пошаговый запуск проекта (How to Deploy / Run)

### 1.1. Предварительные требования
* **Python** версии 3.10 или выше (проект протестирован на Python 3.14);
* Менеджер пакетов `pip`;
* Терминал (PowerShell, Bash или командная строка Windows).

### 1.2. Создание и активация виртуального окружения (рекомендуется)
```bash
# Создание виртуального окружения venv
python -m venv venv

# Активация окружения:
# Windows (PowerShell):
.\venv\Scripts\Activate.ps1
# Windows (CMD):
.\venv\Scripts\activate.bat
# Linux / macOS:
source venv/bin/activate
```

### 1.3. Установка зависимостей
Установите необходимые библиотеки (Django 5.2, flake8, pytest):
```bash
pip install -r requirements.txt
```

### 1.4. Инициализация базы данных SQLite
Перед первым запуском веб-приложения (или для сброса данных к эталонному состоянию) выполните импорт данных из JSON в SQLite:
```bash
python -m db.import_json
```
*Скрипт создаст файл `data/preserves.sqlite`, накатит DDL-схему из `sql/schema.sql` с внешними ключами и наполнит таблицы данными из старых JSON-файлов.*

### 1.5. Запуск веб-сервера Django
Запустите встроенный сервер разработки:
```bash
python manage.py runserver
```
После запуска откройте в браузере: **[http://127.0.0.1:8000/](http://127.0.0.1:8000/)**

### 1.6. Запуск консольного приложения (ПР1–ПР3)
Консольный интерфейс полностью сохранен и работоспособен:
```bash
python main.py
```

### 1.7. Проверка качества кода и тестов
```bash
# Запуск автоматизированных тестов pytest (17 тестов)
pytest -v

# Проверка соответствия стандартам PEP 8 линтером flake8
flake8 --extend-exclude=venv
```

## 2. Сущности предметной области и связи

Предметная область — **домашнее консервирование и учет запасов в погребе**. В системе выделены 3 ключевые сущности, образующие иерархическую связь:

```text
┌───────────────────────┐
│     Product (Сырье)   │
│   id, name, category  │
└───────────┬───────────┘
            │ 1
            │
            │ N (один продукт может быть основой для многих рецептов)
            ▼
┌───────────────────────────────────────┐
│         Preserve (Заготовка)          │
│ id, name, product_id, recipe_notes    │
└───────────────────┬───────────────────┘
                    │ 1
                    │
                    │ N (по одному рецепту может быть закатано много партий в разные даты)
                    ▼
┌────────────────────────────────────────────────────────┐
│                   Batch (Партия банок)                 │
│ id, preserve_id, production_date, quantity, is_consumed│
└────────────────────────────────────────────────────────┘
```

### 2.1. `Product` (Базовое сырье / Ингредиенты)
* **Назначение:** Каталог сырья, из которого готовятся заготовки (овощи, фрукты, ягоды и др.).
* **Поля в БД (`products`):**
  * `id` — уникальный первичный ключ (INTEGER PK AUTOINCREMENT);
  * `name` — наименование продукта (TEXT NOT NULL), например: *«Огурцы»*, *«Томаты»*;
  * `category` — классификационная категория (TEXT NOT NULL), например: *«овощи»*, *«ягоды»*.
* **В коде:** Представлен ООП-классом `models/products.py` (ПР3) и таблицей `products` (ПР7).

### 2.2. `Preserve` (Вид заготовки / Рецепт)
* **Назначение:** Описание конкретного вида консервации. Ссылается на исходный продукт.
* **Поля в БД (`preserves`):**
  * `id` — уникальный идентификатор (INTEGER PK AUTOINCREMENT);
  * `name` — название заготовки (TEXT NOT NULL), например: *«Маринованные огурцы»*;
  * `product_id` — внешний ключ к таблице `products(id)` (INTEGER NOT NULL FK);
  * `recipe_notes` — кулинарные заметки, особенности рецепта (TEXT NOT NULL).
* **В коде:** ООП-класс `models/preserves.py` и таблица `preserves`.

### 2.3. `Batch` (Партия банок в погребе)
* **Назначение:** Физическая партия заготовленной продукции с конкретной датой выработки и количеством банок.
* **Поля в БД (`batches`):**
  * `id` — номер партии (INTEGER PK AUTOINCREMENT);
  * `preserve_id` — внешний ключ к таблице `preserves(id)` (INTEGER NOT NULL FK);
  * `production_date` — дата изготовления в формате `ГГГГ-ММ-ДД` (TEXT NOT NULL);
  * `quantity` — текущее количество банок в наличии (INTEGER NOT NULL CHECK >= 0);
  * `is_consumed` — флаг расхода (INTEGER 0 или 1, где 0 — активна, 1 — полностью израсходована).
* **В коде:** ООП-класс `models/batches.py` и таблица `batches`.

## 3. Архитектура веб-приложения

### 3.1. Разделение по приложениям (Django Apps)
* **`homepage`** — визитная карточка системы: сводные показатели погреба, описание назначения сервиса, ссылки на основные разделы;
* **`preserves`** — каталог видов консервации и справочник сырья:
  * `/preserves/` — список рецептур;
  * `/preserves/<int:preserve_id>/` — карточка заготовки;
  * `/preserves/products/` — таблица базового сырья с подсчетом связанных заготовок;
* **`batches`** — управление физическими запасами:
  * `/batches/` — список активных партий;
  * `/batches/<int:batch_id>/` — карточка партии с отображением сырья и заготовки;
  * `/batches/search/` — параметризованный поиск по дате и статусу доступности;
  * `/batches/statistics/` — агрегированная статистика по погребу (SUM/COUNT/GROUP BY).

### 3.2. Шаблонизация (Django Template Language — DTL)
1. **Наследование:** Все страницы расширяют `templates/base.html` (`{% extends 'base.html' %}`), задавая блоки `{% block title %}` и `{% block content %}`.
2. **Включение компонентов (Include):**
   * `templates/includes/navigation.html` — главное меню (все URL строятся строго через `{% url 'namespace:name' %}`);
   * `templates/includes/batch_status.html` — цветной бейдж статуса партии (зеленый «Активна» / серый «Израсходована»).
3. **DTL-фильтры и циклы:**
   * `{% for ... in ... %} ... {% empty %} ... {% endfor %}` — гарантирует корректный вывод даже при пустых выборках;
   * `|length` — вывод количества элементов в списках;
   * `|default:"Нет данных"` — защита от пустых полей;
   * `|date:"d.m.Y"` — человекопонятное форматирование дат производства (например, `10.09.2026`).
4. **Статика (`static/`):**
   * `css/style.css` — оформление карточек `.preserve-card`, шапки и бейджей;
   * `js/main.js` — авто-вычисление года в копирайте футера;
   * `img/logo.png` — графический логотип.

### 3.3. Слой базы данных и отказ от ORM (ПР7)
В соответствии с ТЗ **Django ORM намеренно не используется**. Все запросы к БД выполняются через стандартный модуль `sqlite3`:
* Модуль подключения `db/database.py` возвращает соединение с `row_factory = sqlite3.Row` (обращение к столбцам по именам);
* Включена принудительная поддержка внешних ключей: `PRAGMA foreign_keys = ON;`;
* Все пользовательские параметры фильтрации передаются исключительно через кортежи параметров `execute(sql, [param])`, исключая SQL-инъекции.

## 4. Шпаргалка для защиты перед преподавателем

### Вопрос 1: «Почему вы не использовали Django ORM (models.py)?»
> **Ответ:** По техническому заданию Практической работы № 7 требовалось освоить работу с реляционной базой данных SQLite на низком уровне — через язык SQL и стандартную библиотеку `sqlite3`. Мы самостоятельно спроектировали DDL-схему с ограничениями `FOREIGN KEY`, `NOT NULL`, `CHECK`, написали скрипт миграции данных `executemany` и библиотеку из 12 сырых SQL-запросов (`sql/queries.sql`), которые интегрированы во `views.py`.

### Вопрос 2: «Как защищено приложение от SQL-инъекций (SQL Injection)?»
> **Ответ:** Конкатенация строк и f-строки для подстановки значений параметров в SQL полностью исключены. Все параметры (например, `preserve_id` из URL или параметры формы `date` и `status` из `request.GET`) передаются в метод `cursor.execute(sql, params)` в виде параметров-заполнителей `?`. При этом СУБД SQLite самостоятельно экранирует и типизирует аргументы.

### Вопрос 3: «Зачем в `db/database.py` настраивается `conn.row_factory = sqlite3.Row`?»
> **Ответ:** По умолчанию курсор `sqlite3` возвращает строки в виде простых кортежей (tuples), где доступ к значениям возможен только по числовым индексам (`row[0]`, `row[1]`), что неудобно и ненадежно. Настройка `row_factory = sqlite3.Row` позволяет обращаться к полям строки по именам столбцов (`row['name']`, `row['quantity']`), что также идеально согласуется с шаблонизатором Django DTL.

### Вопрос 4: «Почему в SQLite потребовалось явно вызывать `PRAGMA foreign_keys = ON`?»
> **Ответ:** В СУБД SQLite в целях обратной совместимости с устаревшими версиями проверка внешних ключей по умолчанию отключена. Команда `PRAGMA foreign_keys = ON;` принудительно включает контроль ссылочной целостности: база данных не позволит создать заготовку с несуществующим `product_id` или удалить продукт, на который ссылается рецепт (`ON DELETE RESTRICT`).

### Вопрос 5: «Какие сложные конструкции SQL реализованы в проекте?»
> **Ответ:** В файле `sql/queries.sql` и во `views.py` реализованы:
> 1. **Двойные JOIN:** связь `batches` &rarr; `preserves` &rarr; `products` в карточке партии;
> 2. **Агрегация:** `COUNT()`, `SUM()`, `COALESCE()` для суммирования банок;
> 3. **GROUP BY:** группировка остатков банок по видам заготовок в статистике;
> 4. **HAVING:** фильтрация заготовок, по которым закрыто более 2 партий;
> 5. **Подзапросы `NOT IN`:** поиск рецептов, по которым в данный момент нет активных партий в погребе;
> 6. **LIMIT и ORDER BY:** ранжирование запасов по популярности.

### Вопрос 6: «Как обрабатывается ошибка 404, если запрошен несуществующий ID?»
> **Ответ:** 
> * На уровне представлений: если запрос `SELECT ... WHERE id = ?` возвращает `None`, вызывается функция `render(request, '404.html', {'message': ...}, status=404)`.
> * На глобальном уровне маршрутизации: в корневом `config/urls.py` зарегистрирован `handler404 = 'config.urls.custom_page_not_found'`, возвращающий стилизованный шаблон `404.html` со статус-кодом HTTP 404.

### Вопрос 7: «Не сломались ли автоматические тесты из ПР3?»
> **Ответ:** Нет, все 17 тестов из `tests/` полностью проходят проверку (`pytest`). Консольная логика и ООП-модели сохранены в проекте, обеспечивая плавную эволюцию кодовой базы от консольного приложения к современному веб-сервису.
